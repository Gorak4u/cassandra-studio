================================================================================
 CASSANDRA STUDIO - REQUIREMENTS SPECIFICATION
 Version 1.1 (draft)                                         Date: 2026-10-08
================================================================================

Working name : Cassandra Studio
Product type : Cross-platform desktop application (GUI), plus an optional
               headless "Studio Server" for work that must keep running when
               no desktop app is open (schedules, alerts, history, team use).
Purpose      : One tool to connect to, monitor, query, operate, back up,
               repair, diagnose and benchmark any number of Apache Cassandra
               clusters, regardless of the Cassandra or Java version each one
               runs. It replaces day-to-day use of the separate tools listed
               in section 1.1.

Requirement IDs use these prefixes:
  CON  connection management          MON  monitoring and graphs (JMX)
  CQL  query editor and data tools    SCH  schema / object browser
  OPS  cluster operations (nodetool)  SEC  users, roles, security
  ALR  warnings, errors, alerts       SRV  Studio Server (team / always-on)
  REP  repair management (Reaper)     BAK  backup and restore (Medusa)
  GCL  GC log analysis (GCViewer)     JVM  JVM diagnostics (profilers)
  BLK  bulk load / unload (DSBulk)    STR  stress / benchmark
  SST  SSTable inspection             PRF  query & data-model diagnostics
  AUD  Cassandra audit / query log    CFG  config drift and upgrades
  MIG  schema migrations              PRV  provisioning integration
  RUN  estate script runner           CAP  capacity planning
  NFR  non-functional
Priority: [M] must have (MVP)   [S] should have (v1.x)   [C] could have (later)


--------------------------------------------------------------------------------
1. BACKGROUND AND PROBLEM STATEMENT
--------------------------------------------------------------------------------
The estate runs many Cassandra clusters across customers and environments
(dev / staging / nonprod / prod), with mixed versions:

  Cassandra : 3.11.x, 4.0.x, 4.1.x, 5.0.x
  Java      : 8, 11, 17

Today, operating them needs several tools: cqlsh, nodetool over SSH,
DBeaver/DevCenter for queries, and Prometheus/Grafana for metrics. None of
them gives a single view per cluster, and DevCenter is discontinued.

Facts about the current nodes that shape this design:
  - JMX (port 7199) is bound to localhost only (LOCAL_JMX=yes, no auth).
    A desktop tool CANNOT reach JMX directly over the network.
  - Every node runs the Prometheus jmx_exporter agent on port 7071 (HTTP).
  - Client traffic (CQL, port 9042) may use TLS and PasswordAuthenticator.
  - Operators reach nodes over SSH.
The tool must therefore support more than one way of reading JMX (see CON-6).

--------------------------------------------------------------------------------
2. SCOPE
--------------------------------------------------------------------------------
IN SCOPE
  - Apache Cassandra 3.11, 4.0, 4.1, 5.0 (and later versions as released).
  - Connection management, monitoring, CQL editor, schema browser, data
    editing, import/export, nodetool-style operations, user/role management.
  - Repair scheduling, backup/restore, GC log analysis, JVM diagnostics,
    bulk load/unload, stress testing, SSTable inspection, query and data-
    model diagnostics, audit/query logs, config drift, schema migrations,
    capacity planning, estate script runner (sections 4.9 - 4.22).
  - Provisioning and node lifecycle THROUGH the existing tooling (Puppet
    control repo, Rundeck): Studio triggers and tracks, it does not
    re-implement them (PRV).
  - Optional Studio Server for always-on and team features (SRV).
  - Installers for Windows, macOS (Intel + Apple Silicon), Linux (Ubuntu/
    Debian .deb, RHEL/Rocky .rpm, generic AppImage); Studio Server as a
    container image and Linux package.

OUT OF SCOPE
  - Non-Cassandra databases (MySQL, Postgres, ...). "All features of DBeaver"
    means the DBeaver feature set APPLIED TO CASSANDRA, not multi-database.
  - Relational-only features (ER diagrams with foreign keys, joins, SQL
    query builder) - Cassandra has no such concepts.
  - Creating machines or writing Puppet code; Studio calls the existing
    provisioning flow instead (PRV).
  - DataStax Enterprise-only features (Search, Graph, Analytics).
  - Replacing Prometheus/Grafana as the estate's long-term metrics store;
    Studio can READ from Prometheus (MON-23) and keeps its own history only
    for its dashboards (SRV-4).

3. USERS
--------------------------------------------------------------------------------
  DBA / SRE        : monitors health, runs repairs/compactions, manages users.
  Developer        : browses schema, runs queries, edits test data.
  Read-only viewer : looks at dashboards and data, cannot change anything.
  Platform admin   : runs Studio Server, manages team access (SSO/RBAC),
                     shared connections and schedules.

4. FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

4.1 CONNECTION MANAGEMENT (CON)
-------------------------------
CON-1 [M] Create, edit, clone, delete and test a connection. A connection is
          one CLUSTER, defined by one or more contact points (host:port).
CON-2 [M] Organise connections in a tree of folders, e.g.
            Customer > Environment > Cluster > Datacenter
          with drag-and-drop, rename, search/filter and colour tags.
CON-3 [M] Mark each connection with an environment (DEV/TEST/STAGING/PROD).
          PROD connections show a red banner and ask for confirmation before
          any write, DDL or operation (see NFR-SAFE).
CON-4 [M] CQL connection settings per connection:
            - username/password (PasswordAuthenticator), or none
            - TLS: on/off, truststore/keystore (JKS/PKCS12/PEM), host
              verification on/off, client certificate (mTLS)
            - protocol version: auto-negotiate, or force v3/v4/v5
            - local datacenter (for load balancing), default consistency,
              request timeout, page size
CON-5 [M] Auto-discover all nodes of the cluster from the contact points
          (system.peers / system.peers_v2), with DC, rack, version, tokens.
CON-6 [M] JMX access method, selectable per connection (node-level overrides
          allowed):
            a) Direct JMX/RMI       host:7199, optional user/password, SSL
            b) JMX over SSH tunnel  SSH to node, then localhost:7199
                                    (default for this estate)
            c) jmx_exporter HTTP    read http://node:7071/metrics
                                    (read-only metrics, no operations)
            d) None                 CQL-only connection
            e) Cassandra Sidecar    Apache Cassandra Sidecar HTTP API,
                                    where deployed (4.0+); used for
                                    operations, SSTable upload and health
                                    without SSH
CON-7 [M] SSH settings for (b): user, port, key file / ssh-agent / password,
          optional jump host (bastion), known_hosts checking.
CON-8 [M] Secrets (passwords, key passphrases) are stored in the OS keychain
          (Windows Credential Manager, macOS Keychain, Linux Secret Service),
          never in plain text in the config file.
CON-9 [M] Import/export connections as a file (JSON/YAML) WITHOUT secrets,
          so a team can share one connection list.
CON-10[S] Import clusters from cassandra-control-repo Hiera data
          (data/customers/<c>/<env>/products/cassandra/clusters/*) - seeds,
          DC names and environment become a ready connection tree.
CON-11[S] Connect to several clusters at the same time, each in its own tab.
CON-12[S] Per-connection "read-only" flag that disables all writes.
CON-13[C] Import connections from DBeaver and DevCenter export files.

4.2 MONITORING AND GRAPHS (MON)
-------------------------------
General
MON-1 [M] Metrics come from JMX of EACH node (via CON-6 a/b/c). The tool
          polls on a configurable interval (default 10 s, min 2 s).
MON-2 [M] Version-aware metric catalogue: MBean names and attributes are
          mapped per Cassandra version (3.11 / 4.0 / 4.1 / 5.0) and per GC
          type (CMS, ParNew, G1, ZGC, Shenandoah), so the same graph works on
          every cluster.
MON-3 [M] Graphs show live data plus local history (default 24 h, set in
          preferences), with zoom, pan, time-range picker, pause, and
          per-node / per-DC / cluster aggregation.
MON-4 [M] Export any graph as PNG/CSV.
MON-5 [S] Custom dashboards: user picks any MBean attribute and builds a
          graph; dashboards can be saved and shared as files.
MON-6 [S] Side-by-side compare of two nodes or two time ranges.

Required dashboards / views
MON-10 [M] CLUSTER HEALTH overview
           - nodes Up/Down, Normal/Joining/Leaving/Moving (UN/DN/UJ/...)
           - schema agreement (all nodes on same schema version?)
           - version mix (Cassandra + Java per node)
           - overall status: GREEN / YELLOW / RED with reasons
MON-11 [M] CLUSTER DETAILS: name, partitioner, snitch, DCs, racks, node
           count, total load, keyspace count, Cassandra/Java versions.
MON-12 [M] NODE DETAILS (per node): host ID, address, DC/rack, uptime,
           version, Java version + vendor, heap used/max, off-heap, load,
           number of tokens, thread pools (active/pending/blocked/dropped),
           compactions pending/active, hints, disk usage per data directory,
           CPU and open file descriptors (from JVM OperatingSystem MBean).
MON-13 [M] TOKEN DETAILS: tokens per node, vnode count, token ranges,
           ownership % and effective ownership per keyspace.
MON-14 [M] RING STRUCTURE: graphical ring per DC, nodes placed by token,
           coloured by state and by load; hover shows the node card; click
           opens node details. Table view equivalent to `nodetool ring`.
MON-15 [M] LOAD AND USAGE: data load per node, disk used/free, SSTable
           count, live vs total disk space, load imbalance indicator.
MON-16 [M] GC USAGE AND PRESSURE: GC count and time per collector, GC time %
           of wall clock (pressure), longest pause, heap before/after,
           memory pools (Eden/Survivor/Old/Metaspace), allocation rate.
MON-17 [M] READS AND WRITES: client request rate and latency (p50/p75/p95/
           p99/max) for Read, Write, RangeSlice, CAS; timeouts,
           unavailables, failures - per node and per cluster.
MON-18 [M] KEYSPACE AND TABLE METRICS: per keyspace and per table read/
           write count and latency, partition size (mean/max), cells/
           tombstones per read, SSTables per read, bloom filter false
           positive ratio, key/row cache hit rate, pending compactions.
MON-19 [S] THREAD POOLS and DROPPED MESSAGES (equivalent to `nodetool
           tpstats`) as a live table plus graphs.
MON-20 [S] COMPACTION and STREAMING progress (live, like `nodetool
           compactionstats` / `netstats`).
MON-21 [S] Top tables: "hottest" tables by reads, writes, latency, size.
MON-22 [C] Client connections view (connected clients, driver, version) -
           Cassandra 4.0+ (system_views.clients).
MON-23 [S] Prometheus as a data source: read history for any graph from the
           estate's existing Prometheus (jmx_exporter / node_exporter
           series) instead of, or in addition to, Studio's own history.
MON-24 [S] OS-level panels per node (CPU, load average, memory, disk IOPS
           and latency, network) from node_exporter or over SSH.
MON-25 [S] Virtual tables browser (4.0+): system_views.* shown as live
           tables (settings, caches, thread_pools, sstable_tasks, ...).

4.3 CQL EDITOR AND DATA TOOLS (CQL)  - DBeaver / DevCenter parity
-----------------------------------------------------------------
CQL-1 [M] Multi-tab CQL editor with syntax highlighting, auto-complete of
          keywords, keyspaces, tables, columns, functions and types (driven
          by the live schema), bracket matching, formatting, comments.
CQL-2 [M] Run statement under cursor, run selection, run whole script.
          Script mode stops or continues on error (user choice).
CQL-3 [M] Run a query on a CHOSEN NODE: the user picks the coordinator node
          (any node of the cluster) or "auto" (driver load balancing).
          Optionally run the same query on every node and compare results.
CQL-4 [M] Per-query settings: consistency level, serial consistency, page
          size, timeout, tracing on/off.
CQL-5 [M] Result grid: paging (fetch next page / fetch all with limit), sort,
          filter, column resize/hide, copy cells/rows, show collections,
          UDTs, blobs, JSON, timestamps in chosen time zone.
CQL-6 [M] Query tracing view: trace events per node with elapsed time
          (replaces "explain plan", which Cassandra does not have).
CQL-7 [M] Messages/log panel: warnings returned by the server (e.g. large
          batch, tombstone warnings), errors, execution time, coordinator.
CQL-8 [M] Query history (searchable, per connection) and saved scripts
          (folders, open/save .cql files).
CQL-9 [M] Edit data in the grid: insert row, update cell, delete row. The
          tool generates the CQL, shows it, and runs only on confirm.
          Requires full primary key; disabled on read-only/PROD-by-default.
CQL-10[M] Export results: CSV, JSON, CQL INSERT statements, Excel (.xlsx).
CQL-11[S] Import data from CSV/JSON into a table, with column mapping,
          batch size, rate limit and error file (like cqlsh COPY FROM).
CQL-12[S] Parameterised queries (bind variables prompt), prepared statements.
CQL-13[S] Snippets/templates library (create table, select by key, etc.).
CQL-14[S] Warnings before running risky statements: ALLOW FILTERING, missing
          partition key in WHERE, TRUNCATE, DROP, full-table scans.
CQL-15[C] Visual query builder for SELECT on one table.
CQL-16[C] Result diff between two queries / two clusters.

4.4 SCHEMA / OBJECT BROWSER (SCH)
---------------------------------
SCH-1 [M] Tree: Cluster > Keyspaces > Tables / Materialized Views /
          Indexes (2i, SASI, SAI on 5.0) / UDTs / Functions / Aggregates.
          System keyspaces hidden by default, toggle to show.
SCH-2 [M] KEYSPACE DETAILS: replication strategy and factor per DC,
          durable_writes, tables list, size on disk (from metrics).
SCH-3 [M] TABLE DETAILS: columns with type and role (partition key,
          clustering key + order, static, regular), all table options
          (compaction, compression, gc_grace_seconds, TTL, caching, ...),
          indexes, views, size and SSTable stats, and the full DDL.
SCH-4 [M] Create / alter / drop keyspace, table, index, type, view through
          forms; the generated CQL is always shown before it is executed.
SCH-5 [M] Copy DDL of one object or the whole keyspace ("DESCRIBE").
SCH-6 [S] Schema compare between two keyspaces / two clusters, generating
          the ALTER script.
SCH-7 [S] Data model checks: warn on very wide partitions, too many tables,
          secondary indexes on high-cardinality columns, missing TTL with
          TWCS, gc_grace_seconds = 0, RF=1 in production, SimpleStrategy
          in multi-DC clusters.
SCH-8 [C] Visual diagram of tables and UDT usage per keyspace.

4.5 CLUSTER OPERATIONS (OPS)  - nodetool through the GUI
--------------------------------------------------------
All operations run through JMX (method a or b in CON-6). Each one shows the
equivalent nodetool command, asks for confirmation (twice on PROD), streams
progress, and is written to the audit log (NFR-AUD).
OPS-1 [M] Status/info views: status, info, ring, describecluster, tpstats,
          tablestats, tablehistograms, proxyhistograms, gossipinfo,
          compactionstats, netstats, getendpoints <ks> <table> <key>.
OPS-2 [M] Flush, compact (major / user-defined), cleanup, scrub,
          upgradesstables, garbagecollect - per node, keyspace or table.
OPS-3 [M] Repair: full / incremental / sub-range, -pr, by DC, with live
          progress from JMX notifications; cancel running repair.
OPS-4 [M] Snapshots: create, list, clear (per keyspace/table, per node or
          all nodes).
OPS-5 [S] Drain, stop/start gossip, binary (CQL), handoff; disable/enable
          autocompaction; set compaction/stream throughput; set log level.
OPS-6 [S] Decommission, removenode, assassinate, move - expert mode only,
          with pre-checks (enough replicas, no streaming running).
OPS-7 [S] Run an operation on many nodes in sequence (rolling), with pause
          between nodes and stop-on-error.
OPS-8 [C] Scheduled jobs (e.g. weekly repair) - only if not already done by
          the estate's systemd timers.

4.6 USERS, ROLES AND SECURITY (SEC)
-----------------------------------
SEC-1 [M] USER DETAILS: list roles with login, superuser, member-of, and
          granted permissions per resource (LIST ROLES / LIST ALL
          PERMISSIONS).
SEC-2 [M] Create / alter / drop role, change password, grant / revoke role
          and permissions, through forms that show the CQL.
SEC-3 [S] Check system_auth replication: warn if RF is too low or uses
          SimpleStrategy in a multi-DC cluster.
SEC-4 [S] Show which permissions a role effectively has (incl. inherited).
SEC-5 [C] Network authorization (DC-restricted roles, Cassandra 4.0+).

4.7 WARNINGS, ERRORS AND ALERTS (ALR)
-------------------------------------
ALR-1 [M] Built-in health rules, evaluated on every poll, shown as a
          warnings panel and as badges on clusters/nodes, e.g.:
            - node down / not NORMAL / schema disagreement
            - heap > 85 %, GC time > 10 % or pause > 1 s
            - dropped messages, timeouts, unavailables > 0
            - pending compactions > threshold, SSTables per read > threshold
            - disk usage > 80 %, load imbalance > 1.5x average
            - hints building up, pending/blocked thread pools
            - tombstone warnings, large partitions
          Thresholds are editable globally and per cluster.
ALR-2 [M] Server warnings and errors from CQL responses are kept in a log.
ALR-3 [S] Node log viewer: tail and search system.log / debug.log of a node
          over SSH; filter by level WARN/ERROR; highlight known patterns
          (GC pauses, dropped mutations, OOM, compaction errors).
ALR-4 [S] Desktop notifications when a rule turns RED (opt-in per cluster).
ALR-5 [S] Send alerts to Slack / e-mail / PagerDuty / webhook (needs SRV,
          so alerts fire when no desktop app is open).

4.8 STUDIO SERVER - TEAM AND ALWAYS-ON MODE (SRV)
-------------------------------------------------
The desktop app works on its own. Features that must run unattended or be
shared by a team need the optional Studio Server: the same engine, headless,
deployed as a container or Linux service close to the clusters.
SRV-1 [S] Desktop app connects to a Studio Server and then uses it for
          cluster access (no SSH/JMX from laptops needed), or works
          standalone as before. The mode is per workspace.
SRV-2 [C] Single sign-on (OIDC / SAML, LDAP / Active Directory) and role-
          based access: viewer / developer / operator / admin, granted per
          folder or per cluster. Deferred: Q-1 decided no access control for
          now.
SRV-3 [S] Shared, central connection catalogue and saved queries/dashboards,
          with per-user private items (answers Q-2). Secrets held in the
          server's vault (HashiCorp Vault, AWS/GCP secret manager or an
          encrypted local store).
SRV-4 [S] Metric history kept on the server (default 30 days, downsampled
          after 48 h), so graphs survive app restarts and cover all users.
SRV-5 [S] Scheduler for repairs (REP), backups (BAK), health reports and
          custom jobs; alert routing (ALR-5) with silences and escalation.
SRV-6 [S] Central, tamper-evident audit log of every action by every user;
          export to SIEM (syslog / JSON).
SRV-7 [S] High availability: two or more server instances with a shared
          store (PostgreSQL); a lost instance never loses schedules.
SRV-8 [C] REST API and CLI for everything the UI does (automation, CI).
SRV-9 [C] Web UI served by the server (same UI code) for users who cannot
          install the desktop app.

4.9 REPAIR MANAGEMENT - Reaper equivalent (REP)
-----------------------------------------------
REP-1 [M] Repair runs split into token-range segments, run with limited
          parallelism and intensity, retry failed segments, pause/resume/
          abort, live per-segment progress.
REP-2 [M] Full, incremental (4.0+) and sub-range repair; per keyspace,
          table list, DC list, or "primary range only".
REP-3 [S] Repair schedules (e.g. every 7 days, must finish within
          gc_grace_seconds) - run by Studio Server (SRV-5).
REP-4 [S] Repair history and coverage: last successful repair per table and
          per range; alert when a table has not been fully repaired within
          gc_grace_seconds (risk of zombie data).
REP-5 [S] Safety: no repair start when a node is down, when pending
          compactions or streaming are above a threshold, or during a
          configured blackout window.
REP-6 [M] Repair providers, chosen per cluster (Q-6): (a) built-in
          segmented repair (REP-1..5); (b) an existing Cassandra Reaper via
          its REST API - show and control its runs and schedules instead of
          repairing twice; (c) custom repair scripts or systemd timers on the
          nodes. Studio auto-detects what a cluster uses (Reaper URL, timers,
          known scripts) and asks when unsure.
REP-7 [M] Custom repair provider: an admin defines the command to run per
          node or per cluster (e.g. /opt/scripts/range-repair.sh {keyspace}),
          how to read its progress or log, and its success exit code; Studio
          runs it over SSH with the same confirmations, audit and live output
          as built-in operations.

4.10 BACKUP AND RESTORE - Medusa / estate scripts (BAK)
-------------------------------------------------------
BAK-1 [M] Backup providers, chosen per cluster (Q-6: any of these may be in
          use, and Studio auto-detects them where possible):
            a) estate scripts already on the nodes (full-backup-to-s3,
               incremental-backup-to-s3, restore-from-s3, verify-backup,
               backup-status) - S3, GCS, Azure, local
            b) Cassandra Medusa (CLI over SSH, or its gRPC service)
            c) snapshots only (nodetool snapshot)
BAK-2 [M] Backup catalogue: list backups per cluster/node with time, type
          (full/incremental), size, schema version, status, storage
          location, retention and object-lock state.
BAK-3 [M] Run a backup now (cluster, DC or node), with progress and result.
BAK-4 [S] Verify a backup (files present, checksums match) and show a
          "last verified restorable" date per cluster.
BAK-5 [S] Guided restore: whole cluster, one node, one keyspace or one
          table; to the same or to a different cluster; point-in-time when
          commitlog archiving is configured. Dry-run plan shown first; PROD
          restore needs two confirmations.
BAK-6 [S] Backup schedules and retention policies (SRV-5); alert when the
          last good backup is older than the policy allows.
BAK-7 [C] Restore drill report: periodic automatic restore to a scratch
          cluster to prove backups work.
BAK-8 [M] Custom backup provider: an admin defines the backup, list,
          verify and restore commands (with {keyspace}, {table}, {node},
          {snapshot} placeholders) for scripts that are not the estate's
          or Medusa; Studio runs them over SSH with confirmations and audit.

4.11 GC LOG ANALYSIS - GCViewer / GCeasy equivalent (GCL)
---------------------------------------------------------
Live GC metrics from JMX are in MON-16. This group analyses GC LOG FILES,
which hold every single pause and are needed to tune a JVM.
GCL-1 [M] Load GC logs from a node over SSH (current and rotated files) or
          from a local file / zip. Parse both formats:
            - Java 8 (-XX:+PrintGCDetails / PrintGCDateStamps)
            - Java 9+ unified logging (-Xlog:gc*)
          for CMS, ParNew, G1, ZGC and Shenandoah.
GCL-2 [M] Charts: pause time per event over time, heap before/after GC,
          young/old/metaspace occupancy, allocation and promotion rate,
          GC throughput %, concurrent cycle durations.
GCL-3 [M] Summary: total/avg/max/p99 pause, pause histogram, % time in GC,
          number of Full GCs and their causes, humongous allocations (G1),
          to-space exhausted / evacuation failures, safepoint time.
GCL-4 [S] Findings and tuning hints: e.g. "Full GC caused by metaspace",
          "heap too small - old gen > 90 % after GC", "pauses > 500 ms
          exceed read timeout", with the JVM option involved
          (jvm-server.options / jvm11-server.options).
GCL-5 [S] Compare two logs (before/after tuning, node A vs node B) on one
          chart.
GCL-6 [S] Correlate GC pauses with read/write latency spikes (MON-17) on a
          shared time axis.
GCL-7 [C] Show current GC flags of a running node (via DiagnosticCommand
          VM.flags) next to the recommendation.

4.12 JVM DIAGNOSTICS - VisualVM / JMC / sjk equivalent (JVM)
------------------------------------------------------------
All of these work over the existing JMX connection (DiagnosticCommand and
Threading MBeans), so no extra agent is needed on the node.
JVM-1 [M] Thread dump: take one or a series, group by state and by stack,
          highlight blocked/deadlocked threads, compare dumps, export .txt.
JVM-2 [M] Top threads by CPU (like sjk ttop), refreshed live.
JVM-3 [S] Heap histogram (class, instances, bytes) and diff between two
          histograms (leak hunting). Full heap dump to the node's disk with
          a size warning; optional download.
JVM-4 [S] JDK Flight Recorder: start/stop a recording (Java 11+, 8u262+),
          download the .jfr and show CPU, allocation, lock and I/O hot
          spots.
JVM-5 [S] JVM summary: version, vendor, flags, system properties, uptime,
          class loading, compilation, direct/mapped buffer pools, open file
          descriptors.
JVM-6 [C] CPU / allocation flame graph via async-profiler, copied to the
          node over SSH for one run and removed after (opt-in, expert mode).

4.13 BULK LOAD AND UNLOAD - DSBulk equivalent (BLK)
---------------------------------------------------
BLK-1 [M] Unload a table or a query to CSV / JSON (local file or S3/GCS),
          token-range parallel, with progress, rate and error file.
BLK-2 [M] Load CSV / JSON into a table with column mapping, data-type
          conversion, TTL/timestamp options, batch size, rate limit,
          max-errors and a rejected-rows file.
BLK-3 [S] Fast exact row count per table / per token range / per host.
BLK-4 [S] Copy data from one table or cluster to another (unload + load
          without a local file), with throttling.
BLK-5 [S] Jobs run on the user's machine or on Studio Server (large data
          should not cross the user's laptop link).
BLK-6 [C] sstableloader / Sidecar upload for very large imports.

4.14 STRESS AND BENCHMARK TESTING (STR)
---------------------------------------
STR-1 [S] Run cassandra-stress (shipped with Cassandra) or NoSQLBench
          workloads from a wizard: write / read / mixed, user profile YAML
          (the estate's stress-schema.yaml as a starting point), threads,
          rate, duration, consistency.
STR-2 [S] Run from the user's machine, from Studio Server, or on chosen
          stress client hosts over SSH.
STR-3 [S] Live results (ops/s, latency percentiles, errors) next to the
          cluster's own metrics (MON) on one time axis; save runs and
          compare runs.
STR-4 [S] Blocked on PROD connections unless an admin unlocks it per run;
          clear warning on any shared cluster.
STR-5 [C] Workload generator from an existing table's schema and sampled
          data distribution.

4.15 SSTABLE INSPECTION (SST)
-----------------------------
Runs the tools that ship with Cassandra on the node over SSH (or via the
Sidecar), using the node's own Cassandra version.
SST-1 [S] List SSTables per table and node: size, level / bucket, min/max
          timestamp, repaired-at / pending-repair, droppable tombstone
          ratio, estimated partitions, compression ratio (sstablemetadata).
SST-2 [S] SSTable timeline chart (TWCS/LCS/STCS layout) to see why data is
          not being compacted or expired.
SST-3 [S] sstableexpiredblockers: which SSTables block expired data from
          being dropped.
SST-4 [C] Dump one partition from an SSTable as JSON (sstabledump) - read
          only, size-limited.
SST-5 [C] sstableutil / sstablescrub / sstablesplit / sstablelevelreset /
          sstablerepairedset with the node stopped, as expert-mode wizards
          with pre-checks.

4.16 QUERY AND DATA-MODEL DIAGNOSTICS (PRF)
-------------------------------------------
PRF-1 [M] Hot partitions: run nodetool toppartitions / profileload (where
          the version supports it) per table for a chosen period; show top
          keys by reads/writes and largest partitions.
PRF-2 [M] Large partitions and tombstones: table histograms (partition
          size, cell count), tombstone warnings from logs, tombstone scan
          per table (the estate's tombstone-scan as an option).
PRF-3 [S] Slow-query capture: enable/disable slow query logging threshold,
          show slow queries from logs with coordinator and duration.
PRF-4 [S] Query advisor in the editor: show partition key coverage, expected
          partitions touched, consistency vs RF, and warn on IN on
          partition key, unbounded range scans, unlogged multi-partition
          batches.
PRF-5 [S] Compaction analysis: strategy fit per table (e.g. TWCS on TTL
          time-series), backlog trend, compaction throughput vs write rate
          (the estate's compaction-analyzer as an option).
PRF-6 [C] Data-model review report per keyspace, combining SCH-7, PRF-1,
          PRF-2 and PRF-5 into one exportable document.

4.17 CASSANDRA AUDIT LOG AND FULL QUERY LOG (AUD) - Cassandra 4.0+
------------------------------------------------------------------
AUD-1 [S] Enable/disable/configure the audit log per node or cluster
          (included/excluded keyspaces, categories, users).
AUD-2 [S] Search and view audit events (who, what, when, from where, result)
          collected from all nodes, with filters and export.
AUD-3 [S] Full query log: enable for a period, then view captured queries,
          and use fqltool dump / replay / compare to replay them against a
          test cluster (e.g. before an upgrade).
AUD-4 [C] Alerts on audit patterns (failed logins, DDL on PROD, superuser
          use) via ALR-5.

4.18 CONFIG DRIFT AND UPGRADES (CFG)
------------------------------------
CFG-1 [M] Effective config per node: cassandra.yaml settings (virtual table
          system_views.settings on 4.0+, file over SSH otherwise), JVM
          options and flags, OS limits.
CFG-2 [M] Drift report: settings that differ between nodes of the same
          cluster/DC, or differ from the expected values in the Puppet
          control repo's Hiera data.
CFG-3 [S] Change runtime settings that Cassandra allows without restart
          (compaction/stream throughput, trace probability, timeouts on
          4.0+, log levels), with audit.
CFG-4 [S] Upgrade readiness check per cluster, e.g. 3.11 -> 4.0 -> 4.1 ->
          5.0: removed/renamed yaml options, deprecated features in use
          (Thrift, COMPACT STORAGE, old SSTable formats needing
          upgradesstables), Java version compatibility, schema agreement,
          repair status, disk headroom. The estate's
          cassandra-upgrade-precheck as an option.
CFG-5 [S] Rolling-upgrade tracker: shows per node which version it runs and
          the step it is at, while Puppet/Rundeck do the upgrade (PRV).

4.19 SCHEMA MIGRATIONS (MIG)
----------------------------
MIG-1 [S] Versioned migration scripts (folder of .cql files, Git
          repository), applied in order with a history table in the target
          keyspace (compatible with cassandra-migration conventions).
MIG-2 [S] Plan / apply / status per cluster; waits for schema agreement
          after every DDL statement before the next one.
MIG-3 [S] Promote the same migration set DEV -> STAGING -> PROD and show
          which clusters are behind.
MIG-4 [C] Generate a migration from a schema compare (SCH-6).

4.20 PROVISIONING AND NODE LIFECYCLE INTEGRATION (PRV)
------------------------------------------------------
Studio does not build machines or write Puppet code. It drives and tracks
the estate's existing flow.
PRV-1 [S] Read the cassandra-control-repo Hiera hierarchy: show which
          customer / environment / cluster / DC each node belongs to and the
          Hiera values that apply to it (cluster, DC and node layers).
PRV-2 [S] Wizards for add node, remove/decommission node, replace dead
          node, add datacenter, rolling restart: each wizard runs pre-checks
          (RF, disk headroom, streaming, schema agreement), then triggers
          the matching Rundeck job or estate script (decommission-node,
          prepare-replacement, rebuild-node, rolling_restart, drain-node,
          ...), then shows progress from cluster state.
PRV-3 [S] Show and trigger Puppet runs on a node (last run time, status,
          changed resources), via Rundeck or SSH.
PRV-4 [C] Open a Git pull request on the control repo for Hiera changes
          made in a form (e.g. new node file, changed setting) instead of
          editing YAML by hand.
PRV-5 [C] Kubernetes clusters run by K8ssandra / cass-operator: show the
          CassandraDatacenter resource and scale/restart through it.

4.21 ESTATE SCRIPT RUNNER (RUN)
-------------------------------
RUN-1 [S] Catalogue of the ops scripts already installed on nodes by
          Puppet (node_health_check, disk-health-check, table-stats,
          tombstone-scan, compaction-analyzer, query-analyzer,
          jvm-performance-monitor, capacity-planner, cleanup-node,
          clear-cache, ...), each with a description and parameters form.
RUN-2 [S] Run a script on one node, a DC or the whole cluster (parallel or
          rolling); output streamed live per node, saved to history.
RUN-3 [S] Same safety rules as OPS: read-only scripts run freely,
          changing scripts need confirmation and are audited; PROD needs
          the cluster name typed.
RUN-4 [C] Users can add their own scripts to the catalogue (admin-approved
          on Studio Server).

4.22 CAPACITY PLANNING (CAP)
----------------------------
CAP-1 [S] Growth trends per cluster, keyspace and table (data size, write
          rate) and forecast of when disks reach 50 / 70 / 80 % (compaction
          headroom).
CAP-2 [S] "What if" calculator: add nodes, change RF, change compaction
          strategy, change TTL - estimated per-node load and headroom.
CAP-3 [C] Monthly capacity report per cluster, exportable (PDF/HTML).

             negligible load to Cassandra (one JMX connection per node,

NFR-SAFE [M] Safe by default: read-only and PROD flags respected everywhere;

NFR-SEC  [M] Secrets in the OS keychain; TLS everywhere it is configured;

NFR-AUD  [M] Local audit log of every write, DDL and operation: who, when,

NFR-UX   [M] Light and dark theme, keyboard shortcuts, resizable/dockable

NFR-UPD  [S] Auto-update check (can be disabled for offline/air-gapped use).
NFR-I18N [C] Translatable UI strings (English first).
NFR-LIC  [M] Only open-source dependencies with licences compatible with

Production-grade engineering
NFR-SCALE [M] Tested at 500 nodes in one cluster and 100 clusters per

NFR-SSDLC [M] Threat model per release; static analysis and dependency/CVE

NFR-SIGN [M] All installers and the server image are signed (Windows

6. ASSUMPTIONS AND OPEN QUESTIONS
--------------------------------------------------------------------------------
A-1 SSH access to nodes is available to tool users; that is how JMX is
    reached on the current estate (JMX is bound to localhost).
A-2 Users accept the jmx_exporter fallback (CON-6c) gives metrics only, no
    operations.
A-3 Rundeck and the estate scripts installed by cassandra_pfpt are the
    supported way to change nodes; Studio drives them (PRV, RUN, BAK).
A-4 Studio Server can be hosted inside the network that reaches the
    clusters (it needs CQL, SSH/JMX and object-storage access).
Q-1 Who may run operations?
    DECIDED (2026-10-09, owner): open to all for now - no access control.
    Every user may run every operation. Safety confirmations (NFR-SAFE:
    typed cluster name on PROD, read-only connections) and the audit log
    (NFR-AUD) stay, as they prevent accidents rather than restrict users.
    RBAC (SRV-2) is deferred until requested.
Q-2 Shared connection list?
    DECIDED (2026-10-09, owner): file import/export (CON-9) now; a shared
    central catalogue comes with Studio Server (SRV-3, v1.1).
Q-3 Is DataStax Enterprise or ScyllaDB support ever needed?
    DECIDED (2026-10-09, owner): no - Apache Cassandra only for now.
Q-4 Licence of the tool itself: internal-only, or open source?
    DECIDED (2026-10-09, owner): internal / proprietary for now (private
    repository); open-sourcing can be decided later.
Q-5 Is Studio Server in scope for v1.0, or desktop-only first?
    DECIDED (2026-10-09, owner): desktop-only v1.0; Studio Server in v1.1
    (scheduled repair, backup, alerts, shared catalogue).
Q-6 Is a Reaper or Medusa deployment already running anywhere in the
    estate, or are the estate scripts and systemd timers the only ones?
    DECIDED (2026-10-09, owner): it can be anything, and differs per cluster:
    Cassandra Reaper, Medusa, or custom scripts on the nodes. Repair and
    backup therefore use pluggable providers chosen (or auto-detected) per
    cluster - see REP-6, REP-7, BAK-1, BAK-8.

7. ACCEPTANCE CRITERIA (MVP)
--------------------------------------------------------------------------------
1. Install on Windows, macOS and Ubuntu from the release installers.
2. Save 3 clusters (3.11/Java 8, 4.1/Java 11, 5.0/Java 17) in folders by
   environment; secrets land in the OS keychain.
3. Connect to each; health, node, token, ring, load, GC, read/write,
   keyspace and table dashboards show live data via SSH-tunnelled JMX.
4. Run a CQL query on a chosen node, with tracing; export the result to CSV.
5. Edit a row in the grid on a DEV cluster; the same action is blocked on a
   read-only connection and asks for confirmation on PROD.
6. Run flush + repair on one node and see progress; audit log records it.
7. Stop one node: within one poll interval it shows DOWN and a RED alert.
8. Load a Java 8 CMS log and a Java 17 G1 log from nodes over SSH; the GC
   report shows pauses, heap charts and at least one tuning finding.
9. Take a thread dump and a top-threads view from a node via JMX.
10. Run a backup through the estate scripts and see it in the catalogue.
11. Run the drift report on a cluster where one node has a changed
    setting; the difference is shown.

ACCEPTANCE CRITERIA (v1.1 - Studio Server)
1. Log in through SSO; a "viewer" cannot run a write, operation or script.
2. A segmented repair schedule runs overnight with no desktop app open;
   history shows per-segment results and the gc_grace coverage is green.
3. A backup schedule runs; a backup is verified; a table is restored to a
   scratch cluster with the guided restore.
4. A RED alert reaches Slack/e-mail with no desktop app open.
5. Unload a 10 GB table with the bulk tool from the server, then load it
   into another cluster; row counts match.
6. A stress run against a DEV cluster shows its results next to cluster
   metrics; the same run is blocked against PROD.
